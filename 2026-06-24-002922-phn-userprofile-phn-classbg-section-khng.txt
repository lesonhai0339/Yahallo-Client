● Đúng rồi — không nên nhồi vào UserEntity. User nên giữ gọn (identity/auth: id,

  gộp vào UserEntity. Mình đồng ý với bạn về backend.

  Thiết kế đề xuất

  Một entity riêng, ví dụ UserSettings (hoặc UserPreferences), 1–1 với User:

  UserSettings
  ├── id            (PK)
  ├── userId        (FK → User, unique → ràng buộc 1-1)
  │
  ├── theme         enum: dark|light|midnight|sepia|ocean
  ├── bgImageUrl    string?   ← URL S3, KHÔNG lưu base64/data URL
  ├── bgOpacity     float
  ├── bgBlur        int
  ├── bgCoverMain   bool
  │
  ├── fontFamily    string
  ├── fontSize      int / enum
  ├── listView      enum: list|grid
  ├── defaultPageSize  int
  │
  ├── readProgressMode enum: off|ask|always
  ├── retentionDays    int
  ├── maxEntries       int
  │
  ├── createdAt
  └── updatedAt

  Vì sao tách entity riêng (không gộp User)

  - Single Responsibility: User lo identity; UserSettings lo personalization.
  Query auth không phải kéo theo cột settings.
  - Dễ mở rộng: thêm field mới (font, style…) không đụng bảng User.
  - Lazy load: chỉ fetch settings khi cần (vào app / mở trang settings).

  Có cân nhắc dùng JSON column không?

  Nếu settings hay đổi schema và bạn không cần query/filter theo từng field, có
  thể dùng 1 cột JSON (settings jsonb) thay vì hàng chục cột:
  - Ưu: thêm/bớt field thoải mái, không cần migration.
  - Nhược: không validate ở DB, khó index/query theo field.

  Với theme/font/style thì JSON column rất hợp lý vì bạn gần như chỉ "load toàn
  bộ + lưu toàn bộ", không filter. → Mình nghiêng về JSON column cho phần
  presentation settings.

  Nguyên tắc bất biến

  - bgImageUrl chỉ lưu URL (đẩy ảnh lên S3 qua flow presign-upload đã có), tuyệt
  đối không lưu data URL base64 vào DB.
  - Client vẫn cache localStorage để apply tức thì lúc bootstrap, tránh nháy
  theme mặc định trong lúc chờ API; server là source-of-truth, hydrate lại sau
  login.

  POST   /services/presign-upload → (đã có) lấy URL upload ảnh bg lên S3
